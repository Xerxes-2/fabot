# Travel-cost-aware task matching — how the Screeps community assigns creeps to targets

Date: 2026-09-02. All claims verified against primary sources (official docs source, bot code on default branches read locally at the commits current today, first-party blog posts) unless marked **unverified**. Motivating bug: a fresh harvester picked the farther of two sources through swamp because it was first in `room.find` order — fabot's Matcher compares only `(rank, load)` (`src/Core/Decide.fs`, `assignOne`) and never looks at geometry. Sibling survey: `creep-positioning-traffic.md` (movement side); this file covers the assignment side.

## Summary

- **Priority strictly dominates distance everywhere.** No surveyed bot lets a closer low-priority target beat a farther high-priority one: Winsley's deposit loop breaks out as soon as priority drops; harabi's matcher trades a hauler up only on higher priority, then on closeness; The International folds both into one scalar `priority + range` with priorities scaled to dominate. Distance is a *tiebreak within a priority tier* — exactly the `(rank, cost, …)` shape, never `(cost, rank, …)`.
- **Chebyshev range is the community's per-tick cost proxy; true path cost is reserved for slow-changing, cacheable decisions** (which source to mine, remote viability, hauler sizing). This split is universal and explicitly CPU-motivated — the official docs badge `findClosestByPath` "high CPU cost" vs `findClosestByRange` "medium" and `getRangeTo` "low", and `PathFinder.search` is metered at "1 op ~ 0.001 CPU" with a 2000-op default budget.
- **Load balance is done by per-target capacity ledgers, not by a load term in the comparator.** Winsley and harabi decrement a request's remaining amount as creeps are assigned; nobody compares "how many creeps already do this" as a sort key. fabot's Seat capacity is the same idea; the `load` tiebreak is a leftover that geometry can mostly replace.
- **Unreachable targets are rejected by the same machinery that prices them**: a failed/absent path means `undefined`/`Infinity` cost and the target is skipped (Overmind outposts, harabi sources, Winsley franchises). The one bot that *falls back to range when no path exists* (TooAngel's `getClosestSource`) thereby assigns unreachable targets — the anti-pattern our ticket 2 exists to avoid.
- **Assignments are sticky; distance is consulted only at (re)assignment time.** Nobody re-evaluates a standing assignment because something closer appeared mid-task. The one per-tick global rematcher (Overmind's Gale–Shapley logistics matching) is, on current master, dead code — the shipped path is single-sided greedy.

## 0. Engine ground truth: the CPU model that shapes all of this

From the official API docs source (https://github.com/screeps/docs/blob/master/api/source/, rendered at https://docs.screeps.com/api/):

- Every method carries a CPU badge. `RoomPosition.findClosestByPath` and `findPathTo`: "This method has high CPU cost." `findClosestByRange` / `findInRange`: medium. `getRangeTo` / `inRangeTo`: low. (`api/source/RoomPosition.md`, markers `3`/`2`/`1`.)
- `PathFinder.search` `maxOps`: "The maximum allowed pathfinding operations. You can limit CPU time used for the search based on ratio 1 op ~ 0.001 CPU. The default value is 2000." Other defaults: `plainCost` 1, `swampCost` 5, `heuristicWeight` 1.2 (`api/source/PathFinder.md`). So one uncapped single-room search can cost ~2 CPU — comparable to a small bot's whole per-room budget (Winsley reports ~4 CPU/room post-rewrite, §2).
- `findClosestByPath` documents its own algorithm choice: "`astar` is faster when there are relatively few possible targets; `dijkstra` is faster when there are a lot of possible targets or when the closest target is nearby. The default value is determined automatically using heuristics." (`api/source/RoomPosition.md`) — i.e. the engine itself prices "one creep vs many targets" as **a single multi-goal Dijkstra flood from the creep**, the shape fabot's `firstStepToward` already has.

This is why every bot below (a) uses range per tick, (b) caches path lengths when it needs real cost, and (c) computes real cost only for decisions that change on planning timescales.

## 1. Overmind (bencbartlett/Overmind)

### Logistics network: dQ/dt with range as the time term

`src/logistics/LogisticsNetwork.ts` (https://github.com/bencbartlett/Overmind/blob/master/src/logistics/LogisticsNetwork.ts):

- Preference = resource change rate: `resourceChangeRate()` computes `dQ_dt = request.multiplier * choice.dQ / Math.max(choice.dt, 0.1)` over `bufferChoices()` (direct, or via storage/link buffer). Both sides' preference lists sort by it (`requestPreferences`, `transporterPreferences`).
- The **dt term is linear range, not a path**: every leg is `pos.getMultiRoomRangeTo(targetPos) * LogisticsNetwork.settings.rangeToPathHeuristic`, with the setting defined as `rangeToPathHeuristic: 1.1, // findClosestByRange * this ~= findClosestByPos except in pathological cases`. Commented-out `// approximateDistance += Pathing.distance(pos, targetPos);` lines sit right next to it, and `computeNextAvailability()` carries the comment "Report the transporter as being near a logistics target so that Pathing.distance() won't waste CPU" — real pathing was tried and deliberately backed out of the per-tick loop.
- Per-tick memoization: `cache.resourceChangeRate[requestId][transporterName]` and `cache.nextAvailability[transporterName]`, invalidated per assignment (`invalidateCache`); `_matching` is cleared in `refresh()` and lazily recomputed at most once per tick.
- The blog post (https://bencbartlett.com/blog/screeps-4-hauling-is-np-hard/) presents the Gale–Shapley stable matching over these preferences (dQ/dt maximized over buffer choices, "stable matchings are easy to compute - Gale-Shapley runs in O(n²)") and reports "about 30% fewer creeps … total CPU impact is virtually unchanged" vs the rigid predecessor.
- **But on current master the stable matching is effectively dead**: `TransportOverlord.run()` routes every transporter through `handleSmolTransporter`, whose comment reads "Handles small transporters, which don't do well with the logisticsNetwork's stable matching system" and which does "a single-sided greedy selection of all requests" (`_.first(transporterPreferences(...))`). `handleBigTransporter` — the only consumer of `logisticsNetwork.matching` — has no caller (`src/overlords/core/transporter.ts`). Even the flagship stable-matching bot ships greedy-by-(dQ/dt).

### Real path cost where it's cheap to amortize

`src/movement/Pathing.ts`:

- `Pathing.distance(a, b)`: true shortest-path length, cached in `Memory.pathing.distances` under an alphabetized position-pair key, "Cache is probabilistically cleared in Mem" — pay once, reuse for the lifetime of the terrain/layout.
- Used for structural choices, not per-tick matching: outpost selection rejects a candidate room if any source's `Pathing.distance(origin, pos)` is `undefined` **(unreachable)** or `> maxSourceDistance`, else scores by mean distance (`src/Overseer.ts` `handleNewOutposts`); hauler sizing uses `tripDistance = 2 * Pathing.distance(...)` (`src/overlords/situational/hauler.ts`); prespawn lead time uses `Pathing.distance(this.pos, colony.hatchery.pos)` (`src/overlords/Overlord.ts`).

### Hybrid picker

`RoomPosition.findClosestByRangeThenPath` (`src/prototypes/RoomPosition.ts`): if the nearest candidate is more than 4 range away, just use `findClosestByRange`; only when several candidates are within range 4 does it call `findClosestByPath` among the tied ones ("don't clutter up pathing.distance cached values"). Used to pick among transport queue targets (`src/logistics/TransportRequestGroup.ts`). Worker overlords use pure range: `worker.pos.findClosestByMultiRoomRange(targets)` (= `minBy` over multi-room Chebyshev) for repair/build/upgrade target choice (`src/overlords/core/worker.ts`).

## 2. Jon Winsley (task-based, role-free — closest to fabot's Matcher)

### 2020: the general matcher (first-party post, https://www.jonwinsley.com/screeps/2020/09/21/screeps-task-management/)

- Tasks are `TaskAction`s with `TaskPrerequisite`s; unmet prerequisites expand to sub-tasks (`toMeet()`), producing a task tree whose leaves include `MoveAction`s — travel is an explicit costed step in the plan.
- Predicted cost is **range, not a path, from the start**: `MoveAction.cost = (creep) => creep.pos.getRangeTo(this.destination)` — "we're approximating with range, because doing the actual pathfinding gets expensive fast."
- The `SpeculativeMinion` fixes the compounding error of multi-leg plans: "a SpeculativeMinion that predicts the minion's state along the task path … a HarvestAction will increase the SpeculativeMinion's capacityUsed, while a MoveAction will change the SpeculativeMinion's position. Then the cost function can calculate accurately based on the minion's predicted state." So leg 2's range is measured from leg 1's *end* position, and predicted output (remaining capacity) rides along.
- His worked example is exactly fabot's pathology, one level up: greedy sequential assignment gives request A its best minion and strands request B with a far one (A/1: 20, A/2: 25, B/1: 10, B/2: 35 ticks); Gale–Shapley (credited to Bartlett's article) repairs it to the stable pairing.
- Stated CPU verdict: "Even when optimized, this generic route seems slow and CPU-intensive. Managers should try to limit requests, either by issuing tasks to minions directly if the task is well understood or by sending only the highest priority requests."

### The simplifications, in order

- Oct 2020 (https://www.jonwinsley.com/notes/screeps-logistics-overhaul): the exhaustive matcher survives **only for logistics** ("Our stable-marriage algorithm is most relevant for energy Carriers, who have multiple sources and multiple destinations to consider"); worker tasks collapse to a single Task where "picking the best minion is a matter of a) distance from the task and b) the minion's active parts." Prerequisites like `MustBeAdjacent` are deleted; getting there becomes part of running the task.
- Aug 2021, "The Great Purge" (https://www.jonwinsley.com/notes/screeps-great-purge): the task system itself is scrapped after a Discord exchange ("klimmesil mentioned that Tigga had said task-managed scripts weren't worth the effort" — secondhand within the post; Tigga's own statement **unverified**). "My great weakness thus far has been the temptation to overengineer a complex flexible solution, only to later discover that a simple hard-coded solution is both more efficient and more effective." Result: "closer to 4 CPU for one room instead of 11."

### The mature bot: ledgers + cached route cost + feasibility rejection

`glitchassassin/screeps` (archived July 2023), `src/Missions/Implementations/LogisticsMission.ts`:

- `findBestDepositTarget`: candidates sorted by priority descending with `if (priority < bestPriority) break;` — **distance can never promote a target across a priority tier**. Within the tier, `distance = getRangeTo(creep.pos, target.pos)` (memoized Chebyshev, `src/Selectors/Map/MapCoordinates.ts`) prefers the closer target as long as its deliverable amount is comparable; amount wins when the closer target can't absorb the creep's load. Assignment writes a reservation: `depositLedger.set(target, reserved + estimatedUsedCapacity(creep))`, so the next creep sees reduced remaining demand — load balancing by ledger, not by comparator.
- `findBestWithdrawTarget`: amount first, then distance as tiebreak, where distance is `getFranchiseDistance(office, source) ?? Infinity` — and two rejections: `if (distance * 2 > maxDistance) continue; // too far for this creep to survive` with `maxDistance = ticksToLive * 0.8` (lifetime round-trip feasibility), and the `?? Infinity` making a source with no planned route unpickable. `withdrawLedger` reserves stock symmetrically.
- `getFranchiseDistance` (`src/Selectors/Franchises/getFranchiseDistance.ts`): true travel cost **without per-tick pathfinding** — walk the *planned franchise road route* summing `road.structureId ? 1 : terrainCostAt(road.pos)`, memoized with a 200-tick TTL. Path geometry comes from the room plan, computed once.
- CPU-adaptive degradation: `if (Game.cpu.bucket < 10000) … deliver everything to storage` — when the bucket sags, target choice collapses to a constant ("optimization to deliver everything to storage when low on CPU").

## 3. The International (The-International-Screeps-Bot/The-International-Open-Source, branch Main)

- Per-tick hauler assignment is **one scalar**: `const score = request.priority + getRange(targetPos, creep.pos)` — lowest wins (`CreepUtils.findRoomLogisticsRequest`, `src/room/creeps/creepUtils.ts`; `getRange` is Chebyshev, `src/utils/utils.ts`). Priorities are numerically scaled so a tier gap outweighs any in-room range (range ≤ 49). Same shape for repair targets: `getRange(creep.pos, structure.pos) + structure.nextHits / 1000`.
- Sticky: the function returns `creepMemory[roomLogisticsRequests][0]` if present — a creep holds its request until fulfilled/invalid; scoring runs only for unassigned creeps. (Anti-thrash identical in spirit to fabot's Assignments map.)
- Harvest assignment is **pre-baked by path distance, not matched per tick**: at plan time `postFastFillerConfig` sorts the room's sources by real path length from the fastFiller anchor — `sortBy(sources, ({pos}) => CustomPathFinder.findPath({origin: pos, goals: [{pos: fastFillerPos, range: 3}]}).length)` (`src/room/remotePlanner.ts`) — so `sourceIndex` 0 is the closest source forever after. Spawn requests carry `sourceIndex` in creep memory (`src/room/commune/spawning/spawnRequests.ts`), with priority `(sourceIndex === 0 ? 0 : 1) + spawnGroup.length` — the close source is staffed first, and the harvester never chooses a source at all.
- Unreachability is handled at the room tier, by time-boxed abandonment: remotes get `abandonRemote` tick counters when they fail (danger, dead paths), decremented per tick, filtering them from use (`src/room/commune/remotesManager.ts`) — a coarser tool than per-assignment checks.

## 4. TooAngel (TooAngel/screeps) — the cautionary fallback

- `RoomPosition.getClosestSource` (`src/prototype_roomPosition.js`): `findClosestByPath(FIND_SOURCES_ACTIVE)` — and if that returns null (no reachable active source), **fall back to `findClosestByRange(FIND_SOURCES_ACTIVE)`, then `findClosestByRange(FIND_SOURCES)`**. The fallback guarantees a target even when no path exists, i.e. it can assign an unreachable source and let the creep grind against a wall. This is the documented-in-code version of the failure our ticket 2 forbids.
- Sticky with a re-pick trigger: `getSourceToHarvest` (`src/prototype_creep_resources.js`) keeps `memory.source` until the source is gone or drained (`source.energy === 0`), then re-picks.
- One genuinely useful heuristic: in swarm mode the selection filter is `(source) => source.pos.hasNonObstacleAdjacentPosition() || this.pos.isNearTo(source)` — a **free-Seat check at assignment time** (`hasNonObstacleAdjacentPosition` scans range-1 tiles for wall/obstacle-structure/creep, `src/prototype_roomPosition.js`). Don't pick a source you can't stand next to.

## 5. sy-harabi (screeps-harabi-bot-sample — the Traffic-Manager author's eco bot)

`src/manageLogistics.js` implements a function literally named `galeShapley(requests, haulers, …)`:

- Each request builds a `MinHeap((hauler) => coordUtils.getRange(request.target.pos, hauler.pos))` — requests propose to haulers **closest-first by Chebyshev range**.
- A proposed-to hauler already holding a match trades up only if the new request has strictly higher priority, or equal priority and the hauler is strictly closer to it — `(priority, range)` lexicographic, distance strictly second.
- ETA-aware demand: on match, `request.amount += request.useRate * getRange(request.target.pos, hauler.pos)` — a consumer keeps draining while the hauler travels, so the amount to deliver grows with distance (dQ/dt reasoning with range standing in for time). Per-target amount decrements are the load balancer.
- Source economics use **real cached paths, computed once**: `generateSourceInfo` (`src/manageSource.js`) paths from the base-plan start position to the planned container; `if (!path) return` — **an unpathable source never gets an info record and is never staffed**. `info.distance = path.length` persists in `Memory.sourceInfos`; sources sort by it (`sourceIds.sort((a, b) => sourceInfos[a].distance - sourceInfos[b].distance)`), remote income/spawn-usage formulas consume it, and hauler lifetime feasibility gates on it (`if (hauler.ticksToLive < 2 * info.distance + 30)` skip).
- His published write-ups (https://sy-harabi.github.io/) cover traffic, defense, quads and terminal-level logistics; no first-party post on this assignment layer was found — the code above is the primary source.

## 6. Cross-cutting patterns

| Pattern | Who / where |
|---|---|
| (a) Range as per-tick proxy; real paths only cached/offline | Overmind logistics (`rangeToPathHeuristic 1.1`), Winsley 2020 (`cost = getRangeTo`) and 2023 (`getRangeTo` tiebreaks), International (`priority + getRange`), harabi matcher (range heaps). Real path cost: Overmind `Pathing.distance` (Memory cache), Winsley `getFranchiseDistance` (planned-road walk, 200-tick memo), International source ordering (plan-time `findPath`), harabi `sourceInfos.distance` (Memory, computed once). |
| (b) Flood direction | No surveyed bot floods per *target* at match time; per-target path costs appear only as plan-time constants (International, harabi, Winsley routes). Per-creep multi-goal search is engine-endorsed (`findClosestByPath`'s `dijkstra` mode "faster when there are a lot of possible targets"). Terrain-static costs are cached indefinitely-ish everywhere (probabilistic/TTL eviction only). |
| (c) Ordering | Priority strictly first, unanimously: Winsley's `break` on priority drop; harabi's trade-up rule; International's scaled scalar. Distance is the intra-tier tiebreak. Far-target starvation is prevented by per-target amount/capacity ledgers (Winsley `depositLedger`/`withdrawLedger`, harabi `request.amount`), by baking staffing into spawn quotas per target (International `sourceIndex`), or by dQ/dt's amount term (Overmind) — never by a "creeps already assigned" comparator term. |
| (d) Stickiness | Assignment decisions run for *unassigned* creeps only: International returns memory request `[0]`; TooAngel re-picks only on target death/drain; Winsley missions fill `assignment.withdrawTarget` when empty. No bot revokes a valid assignment because a closer option appeared. Only Overmind rebuilds its matching every tick (lazily, cached per tick) — and its shipped loop is greedy anyway (§1). |
| (e) Unreachable targets | Reject via the cost machinery: `undefined` distance → reject outpost (Overmind Overseer); `!path` → no source record (harabi); `?? Infinity` + lifetime cap → skipped (Winsley); free-Seat filter before selection (TooAngel swarm). Counter-example: TooAngel's range fallback (§4). Feasibility beyond mere reachability: Winsley's `distance * 2 > ticksToLive * 0.8` and harabi's `2 * distance + 30` reject targets a creep can't *survive* serving. |

## Implications for fabot (Planner → Matcher, pure Core)

1. **Ordering: `(rank, travelCost, load)` — cost as tiebreak inside a rank tier, never across tiers.** This is the unanimous community shape (§6c) and the minimal change to `assignOne`: `List.minBy (fun t -> rank t, costTo creep t, load acc (taskId t))`. Keep `load` as the final key: with cost in second position it only breaks exact-cost ties, which is precisely the residual job the community gives capacity ledgers — and fabot already has the hard cap (Seat-derived `taskCapacities`). Resist folding cost and rank into one scalar (International-style): the F# tuple comparison gives the same dominance guarantee without magic scaling constants.
2. **Cost metric: one Dijkstra flood per unassigned creep, over the Snapshot terrain, to all candidate Work Areas at once.** fabot's position is unusually good: Core already owns a pure Dijkstra (`firstStepToward`) and ADR 0001 already prices swamp (1/5) — the community's reason to fall back to Chebyshev (engine pathing is expensive, uncacheable per tick) largely evaporates when the flood is a pure function over a ≤48×48 projection with a handful of creeps. The engine docs themselves say multi-goal Dijkstra is the right shape when targets are many and near (§0). Refactor `firstStepToward` to return `(firstStep, dist)` per reached goal set, or run one flood per creep that records the cheapest distance into each Task's Work Area; per-target floods only become attractive if creeps ever vastly outnumber tasks (not our regime). If even that is deemed too hot later, the community-proven cheap proxy is Chebyshev range to target minus action range — but measure first.
3. **Caching legal in a pure function: Snapshot-scope memoization.** All community caches key on things that change slower than a tick (terrain, room plan). Inside `decide`, a lazily-built `Map<creepName, DistanceField>` (or just computing each unassigned creep's flood once and threading it through the fold) is observationally pure — same Snapshot, same answer. Cross-tick caching (International/harabi/Winsley-style persistent path lengths) would have to travel through the Assignments-like state the shell persists; don't reach for it until profiling says so — sticky assignments already mean most creeps never re-match, so the flood runs mainly for fresh spawns and completed tasks.
4. **Unreachable targets fall out of the flood for free — make "unreached ⇒ not applicable" the rule.** A Task whose Work Area the creep's flood never reached has no cost; treat it exactly like a failed `applicable` check in the candidate filter (community precedent: `undefined`/`Infinity` ⇒ skip, §6e). This also subsumes the empty-Work-Area case (target ringed by walls/obstacles). Do *not* add a range-based fallback for "no reachable task" — that is TooAngel's bug; an unmatched creep parking (which the Resolver already handles) strictly beats a creep marching at a wall. The observed swamp-harvester bug is fixed by both tickets at once: cost ranks the near source above the far one, and a genuinely cut-off source stops being assignable at all.
5. **Keep stickiness as-is; let cost apply only at (re)assignment.** The community never steals a working creep for a closer target across ticks (§6d) — fabot's kept-Assignments check needs no distance term. Within a single matching pass, Snapshot creep order can still produce Winsley's A/B pathology (§2); with our creep counts the loss is small, and even Overmind ships greedy. If it ever matters, the cheap upgrade is not Gale–Shapley but harabi's trade-up rule: allow a later creep to take a task from an earlier same-tick assignee when strictly closer, re-queueing the loser — a ~10-line change to the fold, same spirit as the Resolver's swap rule.
