# Link footings are a built kind the reservation counts, not a placeable kind reserved per Post

> **Revised by ADR 0035**: "one footing per target" and "this ADR only guarantees the tiles are there" are conditional, and W12S28 was already outside the condition when this was written. A target whose every range-1 tile is gone reserves nothing — the fold had no candidate and said nothing about it (#77). The rule below is unchanged; what ADR 0035 adds is that the shortfall is now recorded on a channel of its own instead of degrading in silence, so "the tiles are there" is a claim a reader can check rather than assume.

ADR 0022 reserved the Link footings alongside the Storage, in one sentence that made three claims the implementation could not keep. **"One per Post"**: `Atlas.posts` is Dual Seats plus the Seats under *built* containers, so at level 0 — the level the reservation is worth the most, because that is when an extension is most likely to take the tile — a Post-anchored rule reserves nothing at all. **"Storage and Link as placeable kinds"**: a placement Intent for a link would be a link the Layout builds, and which footings are filled first, and what the links send where, is RCL5's decision this ADR is not making. **"Reserved before trunks"**: a footing's targets are the container picks, and both container picks are derived from the trunks, which are routed around the reservations — the order has no fixpoint in one pass. Building it as written produced a Layout that churned: with the footings held out of the clustered ordering but absent from the reservation, the cluster reached one tile past the reserved window per footing, onto ground the trunk flood had never dodged, and a footing inside the window kept its tile only while the cluster's gap was still open. The tick RCL4's burst closed every gap, the reservation emptied, the trunk rerouted onto a footing and the Layout emitted a road on a tile it had reserved since level 0, orphaning the roads it moved off. In a sweep of 1,155 plans over random terrain, 156 churned.

We decided three things. **The footing count is the rule's, one per planned source [[container]] plus the controller container plus the Storage** — planned, not built, so the reservation exists from level 0; a room with three sources holds five footings, and "four" was this room's arithmetic, not a constant. **A link is a built kind and nothing else**: `BuiltKind` gains `Link` so a standing one is projected, censused and read back into the footing's own candidates, and `StructureKind` does not, so no placement Intent for a link is expressible. **The tiles are settled after the trunks, but the count is reserved before them**: the clustered window is widened by the footing count, so every tile a footing pushes the cluster onto is inside the set the trunk flood avoids. ADR 0011's precedence then holds in one direction again — reservations come first, a road never sits where a structure will — and the footing's own yield to the trunks is the ordinary one a tile outside the window makes.

## Considered Options

- **Re-flood the trunks once the footings are known** (the two-pass fixpoint ADR 0022's wording implies) — rejected: `trunkPath` is the tick's dearest step, the reason ADR 0017 exists, and paying it twice buys nothing the count already buys. The second pass would also have no termination argument: moving a trunk moves a container pick, which moves a footing.
- **Let the trunk win and re-pick the cluster off the road plan** (the shape that shipped for review) — rejected: it inverts ADR 0011's precedence for exactly the tiles nobody reserved, and it fixes only the collision, not the churn. The tiles still leave and re-enter the flood's avoid set as the cluster is built, so the plan still moves under a Layout that is supposed to be computed whole.
- **Reserve the full RCL4 allowance every tick instead of the still-open gap** — rejected: the gap shrinks by exactly as many tiles as leave the ordering when a site is placed, so the two agree tick after tick. Reserving the full allowance instead re-reserves the built-out ring a second time and widens the avoid set as the colony grows, which is the churn again with the sign flipped.
- **Subtract the [[working ground]] from the footing candidates too** (ADR 0022's own Implementation note, "not itself a Seat") — rejected: it contradicts the same ADR's Solution. A footing on a Seat or an Upgrade tile is the whole point — that is where a link buys the [[anchor]] and the upgraders a transfer without leaving their tile — and dodging working ground would cost the cluster the tile the footing declined.

## Consequences

- The reservation is `storage + tower + extensions + footings` tiles wide, three or four more than ADR 0022 weighed. That is the widening ADR 0022 rejected for RCL5's ten extensions, at a twentieth of the size; the trunks are pushed by at most the ring the footings already occupy.
- `reserved ∪ standing sites` is invariant as the Layout is built out, which is what makes the plan deterministic *across* ticks and not merely across recomputations of one census. The DecideTests surface gains the two cases that pin it: a room whose trunk crosses the cluster asks for nothing the tick after its RCL4 burst, and no clustered structure shares a tile with a trunk road.
- The cluster's re-take of the ordering needs no road-plan filter: every pick is inside the reserved window by construction, so the filter would be unreachable code that hides a broken invariant instead of failing on it.
- A footing outside the window — on [[working ground]], or on the movement colour — is still chosen off the finished trunks, and still stable, because the trunks are.
- One footing per target, and a tile is only ever one target: a Seat that is also the controller container's pick is served once, not twice.
- RCL5 inherits an unchanged question. Which footings are filled, in what order, and what the links send where is still undecided; this ADR only guarantees the tiles are there.
