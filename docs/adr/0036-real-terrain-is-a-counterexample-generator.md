# Real terrain is a counterexample generator swept over spawn positions, never a source of expected values

The [[layout]]'s claims are statements about a whole room's shape — the cluster's nearest-to-spawn ring reaches the controller pocket, the trunks connect, every [[link footing]] target has a tile — and every spatial fixture in the suite is hand-built three to five tiles at a time (`AtlasTests.spatial`). For a single rule that is a feature: a three-tile projection is the rule's documentation. For whole-room geometry it is a ceiling, because a hand-built fixture can only express the failure its author already imagined. #77 is the proof the gap is real and the measure of what it costs: W12S28's `10,43` source container lost its last footing candidate to an extension built in the RCL4 burst, the room held three footings where ADR 0022 and ADR 0027 promise four, and nothing said so. It was found by hand-verification (#65), not by the suite, and the regression fixture ADR 0035 shipped is honest about being an approximation — `sealedPocketColony` walls five neighbours where the live room had a trunk road, the source itself and two standing extensions. The shape is right; the mechanism is weaker than the room's.

We decided **the Layout's whole-room invariants are checked against real room terrain — captured offline once and committed, swept over spawn positions, asserting the rules and never the tiles.**

- **Hermetic, always.** No API call at test time. The seasonal server needs a token, the room changes every tick, and CI without network would go red. The API is an *authoring* tool: capture once, commit the fixture, load it with a pure function.
- **A capture script, not an MCP server.** `scripts/capture-room.mjs` in `observe.mjs`'s own idiom — `screeps-api`'s `gameRoomTerrain` and `gameRoomObjects`, the same authenticated client and shard resolution, `node --env-file-if-exists=.env` behind `npm run capture-room`. Zero new dependencies. A third-party MCP server is more machinery and more trust surface for the same bytes. It writes into the fixture directory (there is exactly one correct destination) and refuses to overwrite without `--force`, so a re-capture that would change a committed fixture is a deliberate act.
- **Reviewable text, one file per room.** A header carrying room, shard, server and tick; a `terrain` section of 50 lines of `0/1/2` **verbatim**, border rows included, so a re-capture of unchanged terrain is byte-identical; an `objects` section as TSV. Raw API JSON diffs unreadably and would pull a JSON dependency into `Core.Tests`. One file rather than two: terrain and objects change on different cadences, but they share one provenance, and sections make the cadence visible without splitting the stamp.
- **The border trim lives in the loader.** `Snapshot.terrainOf` projects only x,y ∈ 1..48 — rows and columns 0 and 49 are exit tiles and are deliberately absent. That single line is the one thing in the loader that must agree with the shell, so it is written there with a comment naming it, not baked into the data where a silent disagreement would be invisible.
- **Only the room's fixed furniture is captured.** Sources, controller, mineral — facts about the room rather than about whoever currently holds it. Not the structures: what the Layout wants is the *empty* room, a live room's objects are somebody's half-built base, and a committed fixture holding another player's base rots in a way nobody can review. The mineral row is kept and ignored by the loader, because a mineral has no `TargetKind` case to enter the projection through.
- **The file keeps the API's real ids; the projection gets readable ones.** A capture should say what the server said, ids included — that is what makes it traceable and a re-capture diffable. The loader assigns `src-0`, `src-1`, `ctrl` in row order and hands them back beside the projection, because a failure message is read by a person.
- **The spawn is the test's, and it sweeps.** A real room's spawn is somebody else's base, and the existing fixtures already treat spawn placement as the author's choice. Sweeping it is the whole point: #77's mechanism — a target whose neighbours all go to trunks, sources and cluster picks — is a function of terrain *and* of where the cluster grew from, so the counterexamples live on the spawn axis. The sweep is deterministic, not fuzzing: a fixed stride over the buildable non-working-ground tiles, no seed, no flake, with W12S28's real spawn always included.
- **Invariants, not golden values.** "Tower at (23,17)" is unreviewable and goes red whenever anything shifts. What is asserted, per room and per swept spawn: every footing target is served (`PlanMemo.UnservedFootings`, ADR 0035); the footing targets number sources + 2, counted as the room's own arithmetic — one container per source, one for the controller, one Storage — rather than as a number written down (ADR 0012, ADR 0022); no clustered structure stands on [[working ground]] (ADR 0022); the trunks carry every source both to the spawn and to the controller's Upgrade Work Area; every tile the Layout paves is one a creep can stand on; no tile is asked for two footprints in one tick; a level never takes a clustered tile back; and a plan recalled from its memo is the plan that was computed (ADR 0017).
- **One listed invariant could not be asserted, and that is its own finding.** "Every reserved footing is off every [[trunk]], off every footing target and off every other footing" is unobservable: `planLayout` is private, a footing is never placed, and the memo carries only the targets the fold *failed* to serve. The served tiles appear nowhere. That is precisely ADR 0035's deferred "record the footings the Layout did place, too", which now has a consumer — #106. The invariant joins the sweep when that field does.
- **The ceilings all came out zero, so there are none.** The plan was a per-room ceiling on unserved targets — a committed number that goes red when the rule regresses and stays green when a room is merely tight — kept in the test beside the room's entry rather than in the fixture header, because the header is capture provenance and a ceiling is a test expectation. The first run reported **zero unserved targets across all 136 (room, spawn) cases**, so the assertion is the strong one and no ceiling machinery exists. What the sweep found instead were two losses of a different shape, pinned rather than excused: see the consequences below.
- **The loader is the test project's.** `tests/Core.Tests/RoomFixtures.fs`, fixtures under `tests/Core.Tests/rooms/` as `Content` copied to the output directory, assertions in a new `RoomInvariantTests.fs`. It builds a `SpatialInfo` through Core's own `isWalkable` rather than restating which structures block a tile (#75), which is what makes a second projection builder safe to have at all. A pure parser in `Core` was the alternative; it would put a parser nothing in the bot ever runs into the Fable build for a consumer that does not exist.
- **Four rooms, measured rather than assumed.** W12S28 (ours, 2 sources), W12S27 and W13S28 (#83's remote targets, ordinary claimable rooms), and W15S25 — a sector centre with three sources and, like every three-source room in the sector, **no controller**. Its controller is synthesised by the test on a fixed tile with a comment, never written into the capture file: a synthesised object inside a capture destroys the provenance the header exists to give. Without a projected controller *position* `planLayout` degenerates — `Atlas.positionOf` returns `None`, the Upgrade Work Area is empty, the trunks route to the spawn only, and the footing count is wrong for reasons that have nothing to do with the rule.

## Considered Options

- **Call the API at test time** — rejected outright, above. It trades a hermetic suite for freshness nobody wants: the room changes every tick, so a test that reads it has no fixed subject.
- **Install a Screeps MCP server** — rejected. `observe.mjs` already carries the dependency, the token and the URL; the endpoints are two lines of a client that is already built.
- **Commit the raw API JSON** — rejected. Unreadable diffs on re-capture and a JSON dependency in `Core.Tests` for data that is a 50×50 grid of three symbols.
- **Golden values — the predicted tiles, asserted** — rejected. It is the #65 comparison written down, and it goes red whenever anything shifts for any reason, which trains the reader to re-baseline rather than to look.
- **One canonical spawn per room** — rejected. It yields one sample per room and re-poses the hand-picked-fixture problem one level up: an arbitrary spawn tile nobody can review, in a room nobody hand-built.
- **A three-source room as the reason to do this at all** — demoted. It was listed in #76 as the most direct return, on the grounds that ADR 0022's "the count is the rule's, never a constant" has no test. Measured against the season server, claimable rooms carry one or two sources and the rooms that carry three — sector centres and Source Keeper rooms — carry no controller and cannot be owned. The rule is still right and the fixture still earns its place, but its instance is hypothetical for the foreseeable future, and the case for this decision is the counterexample generator.
- **Assert monotonicity — the tiles reserved at RCL _n_ are a subset of RCL _n+1_'s** — held back as a scratch check, on the grounds that an invariant that fails for a reason nobody has decided on yet produces an argument rather than a bug. It was then checked and it holds: the full ladder 1→2→3→4→5→8, **680 level pairs across the sweep, zero violations**. So it joined the list, in the cheap form — the 2→4 pair, pinned across every case. The reservation is level-blind by construction (the tower's and the extensions' slots are both sized at the horizon, not at today's level), so what the invariant actually pins is that the *placement* filter only ever adds.
- **Capture a mid-game room with its structures, as an Atlas-flood stress case** — rejected as stated, because the flood is a *terrain* question and these fixtures already give a full 48×48 one. If a structure-loaded stress case is ever wanted, synthesising the structures is better: that is the one place a hand-built fixture wins, because the author controls what is being stressed.
- **Fix whatever the sweep finds inside this work** — rejected. A violation the sweep turns up gets its own issue, its case pinned with a documented ceiling referencing that issue, exactly as #77 came out of #65. Otherwise the ticket's size is unknowable before it starts.
- **A `CONTEXT.md` term for a captured room** — rejected. It is test infrastructure, and the glossary is deliberately free of implementation.

## Consequences

- `scripts/capture-room.mjs` and an `npm run capture-room` entry join `observe` and `upload`; the script is documented in its own header block in that file's style, plus one README line beside `npm run profile`.
- `tests/Core.Tests/rooms/*.room` are the first data files the test project has ever carried, and the first `Content` items in `Core.Tests.fsproj`. Fantomas ignores them, so `npm run format:check` is unaffected.
- `RoomFixtures.fs` compiles first and `RoomInvariantTests.fs` last; the invariants do not grow `DecideTests.fs`, which is already 9,684 lines.
- **The measured sweep.** Stride 6 over plain tiles at least 3 from the furniture, plus W12S28's own spawn tile: **136 (room, spawn) cases** — 43 in W12S28, 17 in W12S27, 34 in W13S28, 42 in W15S25 — each planned four times (the tick; the tick recalled from its own memo, for ADR 0017; a tick on with the road plan standing, so the containers drop; and the same room at RCL2, for the monotonicity pair), so **544 whole-room plans**. The suite goes from 495 tests in 273 ms to **511 tests in about 2.7 s** of test execution, the sweep being essentially all of it.
- **The budget line moved, deliberately.** This ADR first said "under roughly two seconds", and stride 8 would have come in at half that. It is the wrong trade: stride 8 does not contain `6,18`, and `6,18` is where the sweep found #105. A counterexample generator is worth what it catches, so the stride stays at 6, the monotonicity pair is paid for, and the number is recorded rather than the target defended. If the sweep ever needs to get cheaper, the honest lever is fewer *plans per case*, not fewer spawn tiles.
- **What the first run found.** Every footing target served, everywhere — the #77 detector is green across all 136 cases. Two losses of a different shape, both silent, both now pinned in `layout losses the sweep found` and asserted to *still* be losses so the pins cannot outlive their cause: **#104**, a controller whose whole Upgrade Work Area is swamp (W12S27) gets no controller container, so the room plans one fewer container and one fewer footing *target* than the rules promise — and `UnservedFootings` stays empty, because a target that is never constructed is never unserved; and **#105**, the clustered reservation taking one of the two walkable tiles on a tight spawn's doorstep (W12S27 from `6,18`), so an 88-tile source→spawn trunk is dropped whole with nothing recorded. Neither is fixed here.
- **Eight invariants are asserted; the one that is not is #106.** The footing search rule — off every trunk, off every target, off every other footing — stays unasserted until the Layout says which tiles it reserved, because a footing is placed by nothing and recorded nowhere. The determinism invariant is stated over the *memo* rather than over a repeated call: that a pure function returns the same answer twice is not news, and the path ADR 0017 actually risks is the recall.
- Live verification (#65) is not replaced. It catches what terrain alone cannot — timing, a bundle deployed after a burst, another player's structures — and #77 was exactly that. This is the automated form of the same worry, not a substitute for it.
- The fixtures are provenance-stamped and re-capturable, so the day a room's objects move, the diff says which room, which tick, and what changed.
